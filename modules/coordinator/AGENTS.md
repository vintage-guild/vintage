# coordinator module

The autonomous raid coordinator (PLAN §6, #16): on a 5-minute Convex cron it creates upcoming
raids, posts signup messages, reminds non-responders, sends the officer digest, locks signups,
and posts the final roster and addon import string. Maturity: **core**.

## Shape

| Path | Holds |
|---|---|
| `src/contract.ts` | `CoordinatorConfig`, `CoordinatorAction`, `RaidNight`, command names |
| `src/domain/raid-night.ts` | Pure: option labels in the guild zone, `decideRaidNight` (what a closed poll means), the ops message when no raid is made |
| `src/domain/plan.ts` | Pure: `planTick(state, now)` → the actions due now, per raid and rule |
| `src/domain/card.ts` | Pure: the signup post (2x2 role columns), private Roster reply, T-24h party draft, approved party post, and fallback final roster as embeds with spec icons and character-budget packing |
| `src/domain/changes.ts` | Pure: post-digest `#leads` change feed, seated dropout alerts with Standby `[Seat X]` buttons, and lock-time open-seat suggestions |
| `src/domain/server-event.ts` | Pure: a raid as an EXTERNAL Discord server event (name, instance as location, times, a link to the card), its hash, and `MAX_SERVER_EVENTS` |
| `src/domain/kind-words.ts` | Pure: the title, size words, and noun for an event kind (raids keep their own name) |
| `src/domain/render.ts` | Pure: the plain messages (reminder, DM, digest, promotion, import string, failure) and the comp helper |
| `src/domain/summary.ts` | Pure: the raid summary embed (bosses line, who came, what dropped) |
| `src/domain/emoji-ids.ts` | Generated by `scripts/discord-emojis.mjs`: the app's emoji name → id |
| `src/tick.ts` | `runTick(ports)`: settle raid nights → materialize → load → plan → claim → send → record |
| `src/store.ts` | `CoordinatorStore` (config, action log, raid nights), `CoordinatorPolls`, `TickSource`, `TickPorts`, `CoordinatorDeps` |
| `src/commands/` | `coordinator-status|pause|resume|run|config-set|log|repost`, `addon-import-get` (the import string the officer post carries, shared via `buildImportString`: the final roster with groups, and `finalRoster`'s bench with a `benchReason` each; the officer post drops the bench when only that fits one message), and `raid-night-poll` in `raid-night.ts` |
| `src/testing.ts` | Memory store, fake Discord (messages and server events), fake raids, fake polls, state source |
| `convex/` | The `coordinator` component: `config`, `actions`, and `raidNights` tables |

## Rules

| Rule | When | Where |
|---|---|---|
| `post` | as soon as the raid exists | signup channel (or `openSignupChannelId` for open raids), with answer buttons |
| refresh | whenever the post's content changed (not logged) | edits the post |
| cancelled card | the raid was cancelled after its post went up (not logged; its hash keeps it to one edit) | edits the post to **Cancelled · …** with no buttons |
| `remind-<h>h` | each reminder offset, before lock (guild raids only); only the latest due one is sent | signup channel, pings non-responders only, or the `reminderRoleIds` roles with the non-responders named as plain text |
| `dm-<h>h` | the last reminder offset (guild raids only), if `dmReminders`; skips members who opted out and, when `dmRanks` is set, ranks not in it | DM |
| `digest`, `party-draft` | `digestHours` (default 24h) before start (or at lock if over-cap/overcommitted and unapproved) | leads channel (`leadsChannelId`, else `opsChannelId`); seeds `announcedState` for the post-digest change feed; shows **Recommended to sit** when Going signups exceed `event.size` |
| `tentative-check` | if `tentativeCheck` (off by default), the tick after the party draft is sent and before lock; once per member | DM to each member who was Tentative when the draft went out (skips DM opt-outs and, when set, ranks outside `dmRanks`), with **I can make it** / **I can't make it** / **Still don't know** buttons (`tentative-check:<eventId>:yes|no|unsure`, `apps/api/src/discord-tentative.ts`): Going (note cleared), Absent (note kept), or no change. Each answer is logged as a `tentative-answer` action (target the member, detail what they chose) so the Bot tab's log shows it |
| `dropout-*`, `changes-*` | after digest (including while locked and awaiting officer approval), when signups or absences change (group-only moves ignored) | leads channel (seated dropouts get Standby-only `[Seat X]` buttons) |
| `party-post` | once a leader approves the roster (`roster-approve`) and `seated <= event.size` | signup channel; edited in place on moves and promoted into Final Roster at lock (never posted or promoted while overcommitted) |
| `lock` | `lockHours` before start; for a raid, only once a leader approved the roster (`rosterApprovedAt`) | runs `roster-lock`. An unapproved raid stays open past its lock time instead (raid-scheduling decision 17) |
| `approval-hold` | a raid at its lock time with no approved roster; once | leads channel: signups stay open and nothing final goes out until a raid leader or officer clicks **Approve and post**, with the recommended sits or the over-size count |
| `final-roster`, `overcap-approval`, `overcommitted-notice`, `lock-open-seats`, `import-string` | after lock | signup channel (auto-posts at/under cap including voluntary Standby; **held** when unapproved and Going > `event.size` or when `seated > event.size`), leads channel (overcap approval prompt or overcommitted notice when held, for non-raids; open-seat `[Seat X]` suggestions, and addon import string once ready) |
| `raid-night` | a raid-night poll has closed (keyed by the poll id) | runs `raid-create`, or tells the ops channel why not |
| `server-event` | if `serverEvents`, the tick after the post is up | a Discord server event (Events list); edited in place when the raid moves or is renamed (not logged) |
| `server-event-cancel` | if `serverEvents`, the raid was cancelled before it started | sets the server event to CANCELED |
| `raid-summary` | a raid that started in the last `SUMMARY_WINDOW_MS` (7 days) has a recorded export | signup channel; edited in place when a different export replaces the record (not logged) |

- **Claim before send.** Every action is claimed in the component (one transaction) before it
  touches Discord, keyed by (guild, raid, rule, target). Re-running a tick, or two ticks at once,
  never sends anything twice. Keep new rules on this path.
- **Deterministic triggers; AI only for wording** (PLAN §6.2). Timings come from the raids
  schedule (`leadDays`, `reminderHours`, `lockHours`); channels, expected ranks, and DMs from
  `coordinator-config-set`.
- **Non-responders** are members whose rank is in `expectedRanks` and who have no signup.
- **Failures** are logged as `failed`, reported to the ops channel (deduplicated per failure kind
  per hour via `TickPorts.opsAlert` in `apps/api/convex/opsAlerts.ts`, #262), and retried next
  tick. Tick-level step failures (`schedule-materialize`, `raid-night`, `source-load`, and post/event
  edits) are caught and reported to ops too, so a broken schedule does not block tonight's raid
  from posting or locking. A member who doesn't accept DMs (Discord 50007) is logged as skipped.
- Raids work goes through raids **commands** with the system caller (`schedule-materialize`,
  `roster-lock`, `raid-create`), never raids tables.
- **Raid-night polls (#64).** `raid-night-poll` (leader) makes the poll through the
  `CoordinatorPolls` port, which apps/api runs as `poll-create` for that leader, tagged
  `raid-night`. Each option's `value` is its start time. The raid's other details live in the
  `raidNights` table. The tick settles closed ones before `materialize`, so a new raid is posted
  in the same tick. The coordinator imports only polls' contract (the `Poll` type) and learns
  about a closed poll by reading it, not from the event bus, which has no subscribers yet.
- **A raid night's raid is created once.** `createForRaidNight` runs `raid-create` and marks the
  night `created` in one transaction, and the `raid-night` action is claimed per poll. A failed
  attempt leaves the night `pending` for the next tick to retry. A tie, a missed quorum, no votes,
  or a winning time already past creates nothing and goes to the ops channel.
- **Cards are embeds with four role columns in a 2x2 grid** (Tanks/Healers on row 1,
  Melee/Ranged on row 2, padded with inline spacers; Components V2 can't do columns), each
  headed by an outline role icon (`head_tank`, `head_healer`, `head_dps`). Going and Standby
  follow `finalRoster` (`solveEventComp`), so pre-approval overflow shows in **Standby** rather
  than inflating the role columns. The description is the time, the lock and size as `-#`
  subtext, the raid's notes quoted (`> `, a block per paragraph; none when it has none), then
  the status counts spaced with em spaces. The render hash is over the whole message, so a notes
  edit refreshes the post on the next tick. Each field uses line-safe character-budget packing
  (`fitLines`, <= 1,024 chars) ending in `+N more…` only when a field overflows; the **Roster**
  button (`roster:<eventId>`) appears only when someone is hidden and shows everyone privately.
  **Manage** (`manage:<eventId>`, always on the card) gives raid leaders and officers a private
  Move / Cancel menu (`apps/api/src/discord-manage.ts`); everyone else gets a private refusal.
  `tests/card.test.ts` checks a full raid against Discord's embed limits. Icons are the app's
  own emoji (`emoji('status_late')`, `emoji('spec_warrior_protection')`, falling back to
  `emoji('square_<class>')`): our art in `assets/emoji` (`scripts/build-emoji-art.mjs`) plus
  Blizzard class and spec icons; add new ones to `scripts/discord-emojis.json` and re-run the
  upload script. A post deleted in Discord (error 10008) is reposted on the next tick;
  `coordinator-repost` replaces one on purpose and deletes the old message.
- **Words follow the event kind (#151)** through `domain/kind-words.ts`. A raid keeps its own
  title ("Raid night · Molten Core"); other kinds lead with theirs ("Dungeon · Cathedral run ·
  Scarlet Monastery"), on the card, roster, final roster, reminders, DMs, digest, promotion, and
  server event (name, and "5-player dungeon: …" in its description). The size subtext says
  "40-person raid", "5-person dungeon". Raid titles stay unchanged so live cards and server events
  aren't all edited on deploy.
- **Missing buffs are for raids only.** `compFor` uses raids' `eventTemplate` (no requirements
  for other kinds), and the card also drops requirement gaps for non-raids. Role gaps show for
  every kind.
- **No role targets, no role columns.** An event whose targets are all zero (kind `other` with
  no roleTargets) shows one "Going N/size" column instead of three "0/0" ones. Set any count
  and the columns come back.
- **Open `other` events** (no size) drop the "/size" everywhere (`countOf`: "Going 6", "Signups
  locked · 6", the digest's "6 confirmed"), say "open event" in the subtext, and solve the comp
  with everyone going (`compSize`), so there's no size gap. With no instance the title is just
  "Event · Westfall levelling" (`cardTitle`) and the server event reads "Open event."
- **Raid nights carry the kind.** `raid-night-poll` takes `kind` and `roleTargets`, checks them
  like `raid-create`, stores them on the night (optional fields; old nights read as `raid` and
  null), and `createForRaidNight` passes them to `raid-create`.
- **The signup post** shows four role columns (Tanks/Healers, Melee/Ranged), Standby, Tentative
  (names only; tentative reasons stay leader-only in the officer digest and Officers' quarters,
  never on the card or Roster reply), going-only comp gaps (**Missing**), and **Absent** names
  below Missing (declined signups and scheduled absences, plain names, no reasons). The digest
  lists late, tentative, bench, and absence reasons. (Ideas from Raid-Helper:
  docs/research/raid-helper.md.)
- **Weekly assessment (#130).** Off until `coordinator-config-set weeklyAssessment:true`. Then the
  first tick after Monday 16:00 UTC (`assessmentRule`, claimed per week) posts **Weekly roster
  check** to the ops channel: role gaps in the next three raids, the site's open needs (the
  starter needs until saved), and one `recruit:hi:<class>` button per class that could fill a
  tank or healer gap and isn't already high. Suggestions are code; the `wording` port may reword
  the facts (Terra at low effort, a `wording` run in the agent ledger) and falls back to them.
  The button runs `recruiting-set` as the clicking officer (`apps/api/src/discord-applications.ts`).
- **Note triage (#132).** Before the digest goes out, one Decisions request labels every note on
  the raid (`domain/notes.ts`): its kind, and whether it asks an officer for something. Notes
  that do lead the digest under **Needs an officer**; offers to swap get their own line; every
  other note reads as before. `NOTE_THRESHOLDS` come from `tests/fixtures/signup-notes.json`
  (re-score with `pnpm --filter @vintage/coordinator exec tsx scripts/score-signup-notes.ts`).
  No `decisions` port, a paused agent, a refusal, or an error: the digest is exactly the old one.
- Button clicks (`signup:<eventId>:<status>` for accepted, late, tentative, bench, declined) go
  gateway → Convex `POST /gateway/interaction` → `apps/api/src/discord-signups.ts`: a character
  picker when needed, 5/15/30 min buttons for Late, a reason form for Tentative, private replies
  (with comp-solver Standby reasons when overflowed), and an immediate tick so the post refreshes
  in seconds.
- **The raid summary (#221).** The tick source reads completed raids from the last 7 days that
  have a record (`TickState.recorded`: the record, attendance names, and drops read from the loot
  module by apps/api). The embed's description leads with **Bosses: 6/8, 14 wipes, 2h 41m**
  (`bossesLine`: killed out of the matched launch raid, or "3 killed" with none; from the first
  pull to the end of the last attempt), left out for an export without attempts, then the night
  and whose export it was; fields list who came (up to `CAME_CAP`) and the loot (up to
  `LOOT_CAP`). Like the card, its render hash decides edits, and one deleted in Discord is posted
  again on the next tick. A paused coordinator or no signup channel posts nothing.
- **Server events (`serverEvents`, off by default).** The bot needs Discord's Create Events
  permission (a human step, SETUP.md). The Discord event id is the `server-event` action's
  `discordMessageId`, and its `renderHash` is the hash of the fields sent, so the event is
  PATCHed only when the raid's name, time, instance, or card link changes. An event deleted in
  Discord (10070) is recreated on the next tick. A finished raid's event is left alone: Discord
  completes EXTERNAL events at their end time. At most `MAX_SERVER_EVENTS` (25) are held, well under
  Discord's 100. "Interested" is Discord's own and is never read as a signup. Turning the toggle
  off stops all event writes; existing events stay. The tick source always reads cancelled raids
  within the lookahead so cancelled signup cards are redrawn whether or not `serverEvents` is on.
